# 数据迁移与兼容方案

本方案用于把原有乐趣生活、乐趣宝、销售入口和商家后台的数据迁入统一租户系统。迁移不能改变资金、奖励、订单、核销和客户授权的真实含义。

## 一、迁移对象和归属

| 原对象 | 新对象 | 必须补充的归属 |
|---|---|---|
| 公司、商家账户 | `tenants`、`merchant_profiles` | 法定主体、品牌、套餐、数据地区 |
| 门店 | `stores` | tenant_id、门店编码、地理信息来源 |
| 销售、员工、客服 | `users`、`tenant_memberships`、角色分配 | 用户唯一身份、租户、门店范围、角色 |
| 商品、团购 | `products`、`product_variants` | 商家、门店、商品类型、价格来源 |
| 订单、支付、退款 | `orders`、支付与退款表 | 商家支付账户、渠道交易号、金额校验 |
| 消费奖励 | 奖励账户和双重记账流水 | 出资方、规则版本、生效与冲正规则 |
| 会员与客服记录 | `customer_profiles`、会话 | 商家归属、授权依据、保留期限 |
| 小程序配置 | `mini_programs`、版本表 | 商家自有 AppID、授权、模板和线上版本 |

同一个自然人出现在不同商家时，默认是不同租户客户档案。没有明确授权和合法用途，不做跨商家合并。

## 二、五阶段迁移

1. **Expand**：新增租户键、映射表、新状态字段和新接口，旧功能保持可用。
2. **Backfill**：按租户和主键游标分批回填；保存旧 ID 到新 ID 映射、批次、校验摘要。
3. **Verify**：比对行数、金额、订单分布、支付渠道汇总、奖励总额、核销次数和抽样哈希。
4. **Switch**：先切读取，再切写入；灰度租户观察后扩大。切换期间保留旧接口只读或双写校验。
5. **Contract**：在观察期结束、备份恢复验证和业务签字后，删除旧路径；破坏性变更单独发布。

## 三、状态映射

旧系统中的组合状态必须拆分。例如“已支付部分核销退款中”应迁为：订单 `FULFILLING`、支付 `SUCCEEDED`、核销 `PARTIALLY_USED`、退款 `PROCESSING`。无法确定的记录标记 `MIGRATION_REVIEW_REQUIRED` 放入人工清单，不猜测。

## 四、财务校验

每个租户、每日和全量三个层级比对：订单应付、渠道实付、成功退款、奖励发放、奖励使用、奖励冲正、核销次数。金额差异必须为零；若旧系统本身存在差异，迁移前登记为已知差异并由财务确认，不能用新系统补齐来掩盖。

## 五、身份和权限

用户迁移后先获得最低权限。商家负责人由合同或主体管理员确认；店长、客服、财务和核销员按门店重新分配。无法确认归属的历史账号保持禁用，不能默认成为商家负责人。

## 六、客户数据和授权

只迁移有明确来源、用途和保留依据的数据。授权证据无法恢复时，不迁移营销同意；服务记录按必要范围迁移。历史聊天先分级和脱敏，大文本进入受控对象存储，数据库只留引用。

## 七、回滚

应用回滚不等于数据回滚。每次发布明确：可回滚代码版本、兼容读写窗口、已写新数据如何被旧版本读取。不可逆脚本先在生产规模副本演练。禁止恢复整库覆盖迁移开始后的新订单。

## 八、退出迁移

商家终止服务后，AppID 和主体仍归商家。平台提供约定范围的数据导出，建议保留 7 天服务宽限和 30 天导出窗口；届满后按合同、隐私规则和法定保留要求删除或匿名化。平台模板、托管后端和源代码不随数据导出转移。

## 九、验收证据

- 迁移脚本版本和校验和
- 每批租户、游标、成功数和失败数
- 迁移前后 schema 与数据摘要
- 金额和核销对账报告
- 随机抽样记录及新旧页面截图
- 跨租户隔离测试
- 回滚演练记录
- 业务、财务、安全三方签字
