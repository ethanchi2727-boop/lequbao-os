# 事件投递与幂等

## 一、事件写入

领域事件不允许在业务事务提交后才临时拼装。主体状态、业务流水和 `outbox_events` 必须在同一事务写入。事件代表已经发生的事实，名称使用过去式，已发布事件不能修改含义。

每个主体维护递增 `aggregate_version`。同一主体、版本和事件名有唯一约束。生产者把 `partition_key` 设为订单、会话、小程序或交付项目，保证同一主体按顺序处理。

## 二、发布进程

发布进程领取事件的参考 SQL：

```sql
WITH picked AS (
  SELECT id
  FROM outbox_events
  WHERE status IN ('PENDING','FAILED')
    AND next_attempt_at <= now()
  ORDER BY created_at
  FOR UPDATE SKIP LOCKED
  LIMIT 100
)
UPDATE outbox_events o
SET status = 'PROCESSING', locked_at = now(), locked_by = :worker_id
FROM picked
WHERE o.id = picked.id
RETURNING o.*;
```

消息中间件确认接收后标记 `PUBLISHED`。进程崩溃导致 `PROCESSING` 超时的事件可回到 `FAILED`。发布成功与数据库状态更新之间可能重复投递，因此消费者仍必须幂等。

## 三、消费者

1. 验证信封 JSON Schema、事件版本和租户。
2. 在本地事务插入 `inbox_receipts`；唯一键冲突直接返回成功。
3. 执行业务处理并提交。
4. 无法识别的主版本进入隔离队列，不允许静默跳过。

消费者不得信任事件内的权限结论；执行敏感动作前重新检查当前租户、资源范围和授权状态。

## 四、重试和死信

默认退避为 10 秒、30 秒、2 分钟、10 分钟、30 分钟、2 小时，随后每 2 小时一次；最多 12 次且不超过 24 小时。支付、退款、核销和发布命令必须先查询外部结果，再决定是否重试写操作。

死信记录保留事件、消费者、错误分类、首次和最后失败时间、尝试次数及建议动作。重放沿用原 `event_id`，不得伪装成新业务事实。

## 五、版本管理

- 增加可选字段不升主版本；消费者必须忽略未知字段。
- 删除字段、改变类型或含义时发布 `.v2`，并安排双写、消费者迁移和停止旧版本的日期。
- 领域事件和产品埋点分开。领域事件用于业务一致性，埋点用于体验和经营分析，不能用埋点驱动扣款、退款、核销或奖励。

## 六、数据最小化

事件优先传内部 ID、哈希和对象引用。聊天正文、证件、完整地址、手机号和授权密钥不进入消息总线。需要正文的受控消费者凭短时服务身份从源服务读取，并接受租户与用途检查。
