# 建议代码仓库结构

## 1. 首发采用模块化单体

V1 不建议一开始拆成十几个微服务。采用 TypeScript 单仓库、模块化单体、独立异步 Worker：

- 部署和排错更简单。
- 交易、奖励和权限仍能在一个数据库事务内处理。
- 模块通过服务接口和领域事件隔开，后续可以按压力拆分。
- 一键交付、模型调用和外部回调由 Worker 异步处理，不阻塞主接口。

## 3. 推荐技术边界

- 单仓库：pnpm workspace，版本锁定。
- Web：React 与 TypeScript，组件与业务状态分开。
- 小程序：微信原生 TypeScript，共享业务组件和主题配置，不复制商户代码分支。
- API：Node.js TypeScript 模块化服务框架。
- 数据库：PostgreSQL 15 或更高，SQL 迁移、RLS、复合租户外键。
- 缓存与短锁：Redis，只存可丢失数据，不作为资金或奖励真相。
- 文件：对象存储，路径和签名都带租户范围。
- 异步：PostgreSQL Outbox 加 Worker。达到复杂度门槛后再评估专用工作流引擎。
- 观测：结构化日志、Trace ID、指标、告警、不可修改审计。
- 测试：单元、数据库集成、契约、Playwright 端到端和小程序真机回归。

具体框架小版本在开仓时锁定，不随意追新。

## 4. 模块调用规则

- 页面只能调用 API，不直连数据库或 Harness。
- API 从登录态生成租户上下文，不采信请求体里的 tenant_id。
- 模块写操作先校验权限和状态，再写数据库和 Outbox。
- Worker 读取 Outbox 调外部平台，结果写 Inbox 和业务状态。
- Harness 经 Adapter 和 Tool Gateway 调用模块公开能力。
- 插件只能调用授权 API，不能直接读取业务库。
- 分析库只接收脱敏事件，不反向修改交易数据。

## 5. 多租户规则

所有商户业务表、对象、向量、缓存键、队列消息和搜索索引都带 tenant_id。

总部控制台也是受限角色，不默认拥有商户客户、客服和财务数据。临时支持访问需要范围、原因、到期时间和审计。

## 6. 小程序规则

merchant-mini-template 只有一套版本化源码：

- 商户品牌、首页、门店、商品、团购、客服、主题和插件由配置决定。
- 每个商家用自己的 AppID 和主体。
- 体验版、审核、发布、升级、回滚通过微信第三方平台接口处理。
- 禁止复制出 merchant-a、merchant-b 等长期分支。
