# 代码仓库与旧系统升级策略

## 一、明确结论

建议新建“乐趣宝与乐趣生活统一主仓库”，但不是推翻原来的乐趣生活总包。

技术上用新主仓库统一租户、权限、事件、账本、Harness 和两个对外产品；业务上完整继承旧总包的 UI 信息密度、订单、团购、核销、会员、消费奖励、代金券、商家经营和渠道规则。

这不是“只保留新包的几个界面”，也不是“在旧的多入口仓库上一直打补丁”。

## 二、旧产品如何进入新主仓库

| 旧名称 | 新位置 | 处理方式 |
|---|---|---|
| 销售宝 | 乐趣宝·商务中心 | 合并并升级，保留商户归属、交付和提成 |
| 经营宝/商家后台 | 乐趣宝·商家经营中心 | 合并，订单、团购、核销、会员不删除 |
| 城市服务商 | 乐趣宝·区域运营中心 | 合并，改为权限和插件入口 |
| MiniApp Factory | 小程序交付引擎 | 保留能力，隐藏技术名称，改为一键交付工作流 |
| GEO OS | GEO 服务 | 保留并插件化，不承诺收录、排名和流量 |
| Skill Network | 技能、插件、工作流 | 拆分成三种受控能力 |
| 乐趣生活旧 C 端 | 乐趣生活五栏目小程序 | 继承交易和代金券，重做首页与鲜活 UI |

## 三、仓库建议

使用单一主仓库、多应用、共享域模型的结构：

```text
apps/
  lequbao-web
  lequbao-mobile-h5
  lequlife-miniapp
  merchant-miniapp-template
services/
  identity-tenant
  merchant-intake
  billing-revenue
  order-voucher-reward
  delivery-miniapp
  geo
  customer-service
  agent-runtime
packages/
  ui-bao
  ui-life
  permissions
  events
  api-client
legacy-reference/
  v5-readonly
```

`legacy-reference` 只用于对照和迁移，不直接发布。历史代码中稳定的交易和代金券能力，通过回归测试后迁入新域模块，不重写规则。

## 四、迁移顺序

1. 先建租户、组织、角色、权限、审计和事件底座。
2. 迁移商户、门店、会员、商品、团购、订单、核销、支付和退款。
3. 迁移代金券与消费奖励账本，用历史数据对账，同时取消多公司拆分。
4. 上线商务永久收益权、直接成本和月结。
5. 接入 Harness 适配、AI 对话建档、一键交付、GEO、AI 客服和插件。
6. 按租户和区域灰度切换旧入口，指标稳定后再下线旧系统。

## 五、不能直接切换的原因

代金券、奖励、退款、负余额、核销、待结算提成和历史审计不能因界面升级而丢失。切换前必须对比新旧系统的行数、金额、订单、退款、核销、奖励和受益人，差异未解释时不得切换。
