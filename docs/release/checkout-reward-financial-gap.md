# 结算奖励抵扣资金链路 P0 缺口

## 已核对的行为

1. `quote` 在消费者显式选择 `rewardRedemption.action=APPLY` 时建立 `RESERVED` 抵扣投影，并向客户端返回 `cashPayableCents = payableAmountCents - rewardRedemptionCents`。
2. `submit` 创建订单时使用未扣除奖励的 `platform_checkout_groups.payable_amount_cents` 写入 `orders.payable_amount_cents`，随后把 `reward_grants.redeemed_amount_cents` 增加并将抵扣投影标记为 `SETTLED`。这段路径没有写 `REWARD_REDEEM` 双分录账本。
3. 支付意图以 `orders.payable_amount_cents` 向渠道请求金额。支付失败会取消订单并释放库存，但没有释放已 `SETTLED` 的抵扣或冲正奖励账本；现有退款成功路径只冲回该订单新发放的奖励，没有处理该订单已使用的旧奖励。

因此，带奖励抵扣的订单存在按原全额向渠道收款、同时占用旧奖励的风险；失败和退款后的奖励余额也可能不正确。当前开发栈没有已确认商户支付账户，尚未在真实支付渠道观察到该结果；这是由同一代码链路得出的风险判断，不能称为实际发生的资金损失。

## 影响与发布边界

| 项目       | 影响                                                                                                                                                                 |
| ---------- | -------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| 用户和页面 | 乐趣生活消费者的 PAGE-228/229 结算、支付确认、订单详情、退款进度与 PAGE-252 奖励流水。                                                                               |
| API        | `POST /api/v1/life/checkouts/quote`、结算提交、`POST /api/v1/life/payment-intents`、支付/退款回调及订单查询。                                                        |
| 表和事件   | `platform_checkout_reward_redemptions`、`reward_grants`、`orders`、`payment_intents`、`ledger_transactions`、`ledger_entries`、支付/退款 Outbox 事件及订单状态历史。 |
| 权限和历史 | 沿用消费者账号、商户租户与已验证的 RLS；不得重写既有订单、渠道交易、奖励或不可变账本。已有 `SETTLED` 记录需先在真实备份上盘点，按原规则快照和渠道对账结果分类处理。  |

此问题阻断带抵扣的真实支付与受控发布验收。草稿 PR 的绿色自动化检查只覆盖当前已执行路径，不是该资金链路闭环的证据。

在具备授权的隔离旧库恢复环境中运行 `database/preflight/checkout-reward-financial-exposure.sql`，记录已结算抵扣金额、缺少以抵扣记录 ID 关联的 `REWARD_REDEEM` 账本笔数、失败/关闭订单笔数及订单应付高于报价现金额的笔数。脚本只输出汇总，不输出客户或订单标识；CI 用一条合成的已结算、支付失败订单验证各分类计数，不能代表真实旧库的盘点结果。

## 待确认的资金口径

- 抵扣何时从 `RESERVED` 转为真实使用：建议订单提交仅保留可追溯占用，渠道支付确认后才写 `REWARD_REDEEM` 双分录账本；支付失败、超时或取消时释放占用。
- 订单原价、优惠、奖励抵扣与渠道实付的独立字段和恒等式；零现金应付订单如何确认、履约及审计。
- 全额和部分退款时旧奖励抵扣的返还、冲正或人工处理规则，依据原订单与活动规则快照，明确已过期、已再次使用奖励的处理。
- 旧库中已经 `SETTLED` 的记录如何按原订单、渠道交易和奖励账本逐项对账；差异不得自动推定为可退款或可补发。

上述口径涉及金额和退款规则，须由业务/财务确认后才能实现。确认后在隔离 PostgreSQL 中覆盖正常支付、失败/过期、全额/部分退款、重复回调、并发抵扣、零现金、跨账号隔离，以及余额与双分录对账；再以真实备份试迁移、浏览器与真机、渠道沙箱验收。应用回滚保留历史资金事实，差异使用有审批的冲正事务处理。

可审阅的字段、事务和验收实施顺序见 `docs/release/checkout-reward-repair-design.md`；该设计仍待业务/财务确认，不是已批准的资金规则。
