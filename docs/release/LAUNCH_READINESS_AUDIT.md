# V6.1 launch-readiness audit

Date: 2026-08-19

## Release decision

**Not ready to launch.** The repository builds and its local quality gate passes, but the original V6.1 source package defines a launch as ten real end-to-end operating flows across three products. Route generation, eight-state renderers and static prototypes are evidence of contract coverage only; they are not evidence that a user can complete a production transaction.

“Authoritative” means the rendered state is derived from a server API with authenticated, tenant-scoped business data. “Safe contract-only” means production fails closed rather than inventing data. “Prototype-only” means a surface contains static sample business content or simulated production state transitions.

The final reverse audit found and closed two gaps that route-count checks alone did not detect. First, non-demo Workbench chrome and intake panels still contained sample employee/store/task/progress values and browser-only mutation success; production now renders only authoritative session data, hides demo-only tools and counters, routes every shell navigation entry to a real page and fails mutations closed without a live service/session. Second, launch-critical API and Worker provider modules could be silently omitted while the process remained otherwise ready; production startup now requires the complete launch profile and CI proves both candidate images reject missing provider groups.

The same pass removed the Enterprise-WeCom callback's single-Corp/single-member environment binding. Production now calls a credentialed HTTPS configuration boundary that resolves CorpID to tenant-specific callback secrets and resolves the decrypted member to the current tenant/user/store-scoped identity and intake session. Cross-Corp data fails closed; real secret-manager, identity and callback delivery evidence remains part of the controlled identity gate.

The first catalog remediation connected PAGE-207, PAGE-209 and PAGE-221 plus PAGE-267, PAGE-273, PAGE-274, PAGE-276 and PAGE-277 to store-bound consumer catalog APIs. It removed static sample commerce results from both mini-programs and changed every other generic route to fail closed outside an explicitly labelled `demo=1` mode. At that intermediate point these eight pages were authoritative reads while richer descriptions, fulfilment rules and the remaining journey actions were still pending; the later closures below supersede that interim gap.

The next commerce remediation added a platform-level consumer audience, revocable sessions, account-to-merchant customer bindings and an account-isolated cross-merchant cart. PAGE-224 now groups current items by merchant/store and reprices against each merchant tenant; PAGE-237 and PAGE-238 merge and display only orders reachable through active customer bindings. Checkout, discounts, delivery, payment and aftercare were still pending at that checkpoint and are closed by the subsequent sections.

The checkout remediation connects PAGE-227, PAGE-228 and PAGE-229 to an expiring server quote. It rejects stale cart versions, rechecks inventory and price, groups by merchant/store/fulfilment type, snapshots merchant delivery/refund policy, chooses the best active automatic discount, calculates shipping and idempotently creates one merchant-direct order per group. Partial failure preserves completed groups for exact retry and closes the cart only after every group is created. Address editing, signed reward redemption, payment and downstream fulfilment/aftercare were pending at this checkpoint and are covered by the later payment and aftercare closures.

The payment remediation connects PAGE-231 and PAGE-232. Order identity is resolved only through the live platform account-to-merchant link, then the existing payment boundary revalidates that link and uses the owning merchant's confirmed payment account. The mini-program submits the provider credential but displays success only after querying the server-owned order payment state. Real WeChat merchant credentials, callback registration and sandbox reconciliation remain controlled-environment blockers.

PAGE-248 now manages account-isolated delivery addresses. Recipient name, mobile and street line are encrypted with per-write AES-256-GCM nonces and are decrypted only after a live platform session check; the service stays unavailable when its secret-manager key is absent. Cart checkout selects the owner's default address for physical-delivery groups, while pickup and non-physical fulfilment remain address-free.

The aftercare remediation connects PAGE-239, PAGE-240, PAGE-242, PAGE-243, PAGE-245, PAGE-246 and PAGE-252. Refund scope is resolved from the live platform account and owning order, then revalidated inside the refund service; persisted approval/provider progress is displayed without client synthesis. Available verification credentials are short-lived signed tokens, and reward views expose the immutable grant projection including redeemed and reversed amounts. Merchant-template PAGE-284, PAGE-285, PAGE-288–291, PAGE-293 and PAGE-294 use the independently signed, tenant/customer/store-bound consumer session for order list/detail, merchant-direct payment, refund history and verification credentials.

Merchant-template PAGE-280 and PAGE-282 now share the persistent platform cart while requiring both a merchant-bound consumer session and a platform consumer session. The server validates their exact customer mapping, derives tenant/store/source rather than trusting the client, filters every cart and checkout group, and writes `MERCHANT_MINI_PROGRAM` into the order snapshot. PAGE-269, PAGE-297–299, PAGE-304–305 and PAGE-307 now read and mutate authoritative store, customer-service, human-handoff, refund and privacy APIs. PAGE-270 rotates the store-bound consumer session without extending its expiry and PAGE-302 reads the current merchant customer plus the isolated immutable reward ledger projection. All 24 merchant-template leaves are now authoritative in the repository; real WeChat device/provider evidence remains a separate controlled-environment gate.

The final 乐趣生活 closure connects all remaining discovery, category/search, merchant, membership, privacy, subscription-message, assistant, order-tool and ticket pages. City/nearby/map results traverse only the platform account's active merchant links and current active stores; optional location is used for one response and is not persisted. Product provenance requires a current verified versioned report. Invoice title, tax identifier and email use account-scoped forced RLS plus authenticated AES-256-GCM encryption. All 38 乐趣生活 leaves are now authoritative in the repository; real location/provider/device acceptance remains controlled-environment work.

Workbench write remediation converts the already-authoritative delivery, mini-program and customer-service detail pages from read-only projections into bounded command surfaces. Command paths and bodies are page-owned, idempotent and confirmation-gated; generic footer actions are disabled unless a real backend write exists. This improves the completeness of the existing 36 workbench leaves without inflating the authoritative leaf count.

The next workbench closure connects PAGE-009, PAGE-042, PAGE-052, PAGE-054, PAGE-101 and PAGE-134 to the existing employee-scoped conversation, refund, delivery, order-context and mini-program review boundaries. Resource-bound pages require exact IDs, and the dedicated review page exposes only its own submission command. A further six tempting read-only mini-program mappings were deliberately rejected because merely displaying lifecycle state would not complete their named configuration or correction task.

Customer operations closure connects PAGE-105, PAGE-106, PAGE-116, PAGE-119 and PAGE-189. Employee store scope is applied inside each database transaction; list/detail responses are pseudonymous and exclude nickname/mobile ciphertext and object-store references, while reward history comes only from the immutable grant projection and owning-store orders.

Organization governance connects PAGE-072, PAGE-112, PAGE-140, PAGE-141, PAGE-143 and PAGE-193. Tenant-wide membership and role changes require the frozen member/role permissions, MFA and idempotency; platform roles cannot be assigned through a merchant tenant, store roles require a live owning store, the last active merchant owner cannot be removed or suspended, self-suspension is blocked, and suspended-member sessions are revoked atomically. Audit reads exclude before/after payloads, privacy requests expose only processing evidence, and internal notifications retain employee store scope.

Revenue operations connects PAGE-024, PAGE-037–039, PAGE-073, PAGE-137–138, PAGE-152, PAGE-154–157, PAGE-159–160 and PAGE-183–185. Current subscription, plan entitlements, usage, immutable cash/cost/distribution facts, policy versions, permanent rights and transfer state come from tenant-scoped tables. Aggregate reports cannot expose distributions; statement detail requires `distribution.read_all`, costs require `distribution.cost.read`, and rights/transfers require `revenue_right.read_all`. Object-store evidence/agreement addresses, beneficiary identity ciphertext and payout secret references are never returned. PAGE-158 was not counted at this checkpoint because seeing a difference was not the same as resolving it; the final control-plane closure adds its authoritative resolution command.

PAGE-033–035 and PAGE-041 now reuse that same ledger rather than a second commercial projection: permanent right groups show exact holder shares, dispute creation requires at least two claimants and a reason through the existing idempotent governance command, and pending/settled views are filtered distribution statements. Transfer agreement object addresses remain server-only.

Sales and subscription lifecycle closure connects PAGE-026–028, PAGE-030–031, PAGE-045–046, PAGE-049–050 and PAGE-145. Safe processed intake evidence creates owner-scoped opportunities; stable merchant identifiers, contract signer references and collection references are HMAC-only and never returned. Duplicate checks and collection receipts are immutable, quotes use the live plan catalog, contracts require safe document evidence, and financial collection confirmation requires `finance.reconcile` plus MFA. Activation, renewal, plan change and cancellation use separate request/decision/application phases: a requester cannot approve their own change, activation/renewal require signed contracts with net confirmed collection covering the contract, and only the internal worker applies an approved due change. Renewal previews are built from READY immutable monthly reports. Page-owned command forms keep raw identifiers and provider references out of URL parameters and browser history.

Intake and controlled-release closure connects PAGE-011, PAGE-015–021, PAGE-058–060, PAGE-062, PAGE-065, PAGE-075–076, PAGE-164, PAGE-169–170 and PAGE-181. The intake pages reuse the same tenant-scoped session, secure upload, extraction, missing-item, field-source, typed confirmation and audited commit boundaries as the accepted intake journey. CSV candidate IDs and JSON confirmation/configuration values are parsed into typed request bodies rather than URL history. The mini-program pages now exchange one-time authorization codes through password controls, create versioned preview builds from explicit JSON configuration and expose an MFA-protected rollback circuit. Knowledge initialization publishes only versioned, store-scoped, explicitly trusted documents with validity windows. Temporary support uses expiring role assignments, global audit uses redacted audit reads, and launch testing/merchant assistance remain inside the resumable delivery project boundary. No provider result is synthesized locally.

Distribution evidence and appeal closure connects PAGE-040 and PAGE-043. Cost evidence is selected only after tenant or originating-beneficiary scope is proved in the database, then exposed through a five-minute, 20 MB signed object-store URL; the storage key never leaves the API and every read is audited. Cost and revenue appeals are immutable, idempotent records linked to the exact statement and optional cost entry. An originating beneficiary can submit only against their own allocation, while tenant-wide finance retains its broader authorized view. Submitting an appeal never mutates the locked financial facts.

Employee Agent runtime closure connects PAGE-003–007, PAGE-010 and PAGE-167. Conversations and tasks are user-owned and tenant-scoped; prompts stay in object storage under request-hash-bound keys, while task reads expose only redacted plans, evidence and artifacts. Normal tasks are bounded to eight steps, complex/background tasks to twelve, with deadline, tool-call, cost and retry caps. Unknown tool results fail closed. Confirmation and dual-confirmation are one-time, expiring and plan-version-bound; the Worker atomically consumes an approved token before returning a high-risk step for execution, and a different user is required for dual confirmation.

Operational-home closure connects desktop PAGE-079 and mobile PAGE-173 to one authoritative read model. The server derives the tenant's local-day boundary and applies the current employee's tenant or assigned-store scope before counting orders, paid amount, fulfilment, refunds, customer handoffs, notification delivery and delivery exceptions. Agent attention is additionally restricted to the current user's tasks. The response contains aggregated counts and fixed drill-down routes only; it does not expose customer plaintext, object references or client-selected tenant scope.

GEO operations closure connects PAGE-070 and PAGE-126. Health reads apply the employee's live tenant or assigned-store scope and expose profile/channel status, authorization state, freshness, scores and aggregate attention counts without external record IDs, raw provider responses or field hashes. Consistency differences expose only the affected field and lifecycle state. Resolving or ignoring an open difference requires `geo.publish`, MFA, an in-scope row lock and an immutable audit record containing the real actor and reason; a terminal difference cannot be decided twice. PAGE-069 was still outside the count at this checkpoint; the final control-plane closure adds its scoped publish/verify/retry boundary.

Merchant data and knowledge closure connects PAGE-081–084 without creating a second profile authority. Data conversation and uploads reuse the signed, hash-bound and malware-scanned intake material chain; AI organization reads the same durable candidates, sources, conflicts and missing items; pending changes reuse typed field confirmations including publish impact; final publication rechecks the session version, unresolved conflicts, required fields and confirmations before committing. Raw files and object keys remain outside page responses.

Customer-service conversion analysis PAGE-125 reuses the immutable monthly value report rather than calculating browser-side ratios. Its AI reception, human handoff and paid-order metrics retain versioned definitions, generation cutoffs and exact source event IDs, and an optional store remains constrained by the existing employee report boundary.

Group-buy publication PAGE-088 now uses a server-owned `order.manage` and MFA command. The transaction serializes an idempotency key, locks the in-scope group buy at the expected version and rechecks active store, positive price, active variant and unreserved stock before moving DRAFT/OFF_SALE to ON_SALE. An immutable publication receipt provides exact replay, conflicting reuse returns 409, and the audit records the real actor and before/after version without product content leakage.

Customer-service operations closure connects PAGE-103, PAGE-107 and PAGE-110. Duty scheduling validates an active scoped assignee, caps a shift at 24 hours and blocks overlaps under a transaction lock. Customer tasks bind to an existing customer/order or conversation in the same store, retain only a redacted summary, support versioned exact completion and keep deadlines, priority and owner server-side. Quality decisions require MFA and immutable audit; a remediation decision atomically creates a linked knowledge-gap task. The workbench exposes only these page-owned commands and never places customer plaintext in URLs or responses.

The final control-plane closure connects PAGE-069, PAGE-113, PAGE-118, PAGE-130, PAGE-132, PAGE-148, PAGE-151, PAGE-158, PAGE-162 and PAGE-166. GEO publication now requires MFA and exact idempotency, blocks resubmission while an external result is active or unknown and preserves the non-ranking/non-traffic promise. Enterprise-WeCom health retries create durable jobs without exposing credentials. Reward rules version funding, availability, expiry and refund reversal; the selected rule is frozen on each order item before inventory reservation commits, and payment callbacks never consult mutable product policy. Plugin detail exposes the exact published version required for explicit installation, while the ten original V1 skills are repository-attested, bounded to twelve steps/twenty tool calls and cannot expand caller permissions. Platform merchant search excludes legal identity/contact plaintext and crosses tenant RLS only through a security-definer function that revalidates the caller's active platform membership and role. Plan entitlement updates are versioned and existing subscriptions retain their entitlement snapshot. Reconciliation decisions never rewrite payment, refund, order or reward facts. Partner regions and model budgets require platform authority, MFA, version checks, idempotency and audit; model routes store identifiers only, never provider secrets.

The launch gate verifies these counts and must remain red until all 197 launch leaves are authoritative or an explicit product-scope amendment removes a leaf from the frozen P0 release.

## Mandatory release gates

- All 143 original acceptance cases must have build-bound evidence. Current result: 111 local automated, 3 local reviewed and 29 controlled-environment pending.
- All 197 frozen P0 leaves must be authoritative or formally removed from launch scope. Current result: 197 authoritative.
- Because the owner states V5 never served production traffic, every formerly deployable V5 data store must be independently inventoried as zero-production-data and receive a greenfield waiver. Finding any real legacy record invalidates the waiver and restores the full migration rehearsal gate. Reward funding and real-money reconciliation still require business and finance sign-off.
- The seven external gates must pass: PostgreSQL/RLS/concurrency, WeChat publish/rollback, payment/refund sandbox, GEO/plugin isolation, backup/restore, production-shaped performance and on-call/secret/object/privacy infrastructure.
- No stop-release condition may be open, including cross-tenant access, unauthorized high-risk actions, duplicate financial results, unexplained reconciliation differences, unsafe AI actions, callback replay, plugin escape, unaudited mutation or high-severity vulnerability.

## Implementation order from this audit

1. Bind the already-green local PostgreSQL, RLS, concurrency, Worker fault-injection and encrypted-restore results to the exact candidate and obtain independent controlled review.
2. Inventory all V5 deployable stores, approve the zero-data greenfield waiver, and obtain payment/reward funding decisions.
3. Run official WeChat builds, provider sandboxes, network isolation, production-shaped load, physical/WAL recovery, alert delivery and staged pilot release.

No commit or push is part of this audit.
